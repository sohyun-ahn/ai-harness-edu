# design

입력: docs/<이름>/interview.md · `templates/README.md` · 해당 유형의 예시

## 1. 유형 판별
다음 중 하나(둘이면 주된 것 하나 + 보조)를 고르고 근거를 interview.md 의 문장으로 적는다.

| 유형 | 판별 신호 | 예시 (templates/README.md 표) |
|---|---|---|
| 문의 응대 | 질문 → 답변 초안 · 담당자 이관 | inquiry-answer |
| 추출 | 문서 → 항목 · 숫자 추출 · 계산 | spec-quote |
| 보고 | 기록 → 요약 보고서 | weekly-report |
| 비교 | 두 문서 · 두 버전의 차이 | doc-diff |
| 작성 | 메모 · 회의록 → 할 일 · 메일 초안 | meeting-actions · mail-draft |
| 개발 | 코드 · 툴 만들기 | templates/dev/ |

## 2. 예시 참고
`templates/README.md` 에서 해당 유형의 예시를 **읽는다**. 그대로 복사하지 않는다. 인터뷰에 나온 것에 맞는 부분만 가져온다.

## 3. 부품별 설계
부품마다 「넣는다 / 넣지 않는다」를 정하고 이유를 적는다.

| 부품 | 넣는 경우 | 넣지 않는 경우 |
|---|---|---|
| CLAUDE.md | 항상 지킬 원칙 · Skill 호출 표가 있을 때 | — (거의 항상 넣는다) |
| Skill | 반복되는 절차 · 형식이 있을 때 | 한 줄 원칙으로 끝날 때 |
| Hook | 「하면 안 되는 것」이 있고 어기면 피해가 클 때 (원본 수정 · 발송 · 승인 전 쓰기) | 어겨도 되돌릴 수 있을 때 |
| Sub Agent | 여러 건을 나누거나 독립 검토가 필요할 때 | 한 번에 끝나는 일 |

각 부품마다 적는다: 이름 · 역할 · **근거(interview.md 의 어느 답)** · 내용 요지.
근거를 댈 수 없는 규칙은 설계서에 넣지 않는다.

## 4. 시험 설계
- eval 입력 3~5개: 쉬운 것 1 · 함정이 있는 것(7번 답 · 흔한 실수) 2~3 · 해서는 안 되는 요청 1
- 입력마다: 요청문 · 입력 파일(없으면 만들 내용) · 「잘했다」의 확인 항목

## 5. 결과: docs/<이름>/design.md
목차: 이름 · 유형 · 대상 폴더(기본 out/<이름>/) · 부품 표(넣는 것) · **넣지 않는 것과 이유** · 파일 목록 · eval 입력 · 가정 · 확인 필요

## 6. 멈춤
design.md 의 요약(부품 표 · 넣지 않는 것 · 가정)을 보여 주고 이렇게 말한 뒤 **멈춘다**:
「승인하려면 docs/<이름>/APPROVED 를 직접 만들어 주세요. 고칠 곳이 있으면 말씀해 주세요.」
APPROVED 는 절대 만들지 않는다.
